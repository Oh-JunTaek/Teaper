# EunmaStudio 교사 작업 이어쓰기·선택형 동기화 제안서

**작성일:** 2026-08-22  
**결정 대상:** 웹·Windows 로컬·Android 사이의 교사 자료, 문항, 검수, 메모, 쪽지시험 이동 방식  
**전제:** 출시 예정 문항과 수업 자료는 민감할 수 있으므로, 현재의 독립 저장 구조를 자동으로 해제하지 않는다.

> **핵심 제안:** 처음부터 ‘항상 자동 동기화’를 만들지 않습니다. 우선은 교사가 명시적으로 선택한 작업만 암호화해 옮기는 **작업 꾸러미 이관**을 세 플랫폼에 공통 도입하고, 그 사용성이 확인된 뒤에만 **선택형 암호화 동기화**로 확장합니다. 이 방식은 웹에서 준비한 작업을 로컬로 가져가거나, 로컬에서 만든 결과를 웹 작업공간으로 되돌리는 불편을 크게 줄이면서도 무단 전송 위험을 낮춥니다.

## 1. 현재 구조와 해결하려는 불편

현재 웹은 계정별 서버 작업공간, Windows는 PC별 local-only SQLite, Android는 기기 전용 저장소를 사용합니다. 이 분리는 교사 의도 없이 문항·자료·대화 원문이 다른 기기로 이동하지 않도록 하는 보안 경계입니다.[1]

그러나 실제 교사는 다음처럼 기기를 번갈아 사용할 수 있습니다.

| 교사 흐름 | 현재 불편 | 이어쓰기 목표 |
|---|---|---|
| 웹에서 교육과정·PDF·출제 조건 준비 → 학교 PC에서 로컬 모델 생성 | 자료와 조건을 다시 준비해야 함 | 웹에서 선택한 작업 세트를 Windows로 가져오기 |
| Windows에서 민감한 문항 생성·검수 → 웹에서 문서 정리 | 승인 문항을 수동으로 옮겨야 함 | 승인 결과와 근거 요약만 웹에 가져오기 |
| Android에서 수업 직전 메모·쪽지시험 작성 → 웹/PC에서 후속 정리 | 메모·승인 상태가 기기 안에 고립됨 | 교사가 선택한 메모·쪽지시험 세트를 안전하게 전달 |

## 2. 가능한 접근 방식

| 접근 방식 | 교사 경험 | 보안·운영 특성 | 비용·구현 난이도 | 권고 위치 |
|---|---|---|---|---|
| **A. 암호화 작업 꾸러미 내보내기·가져오기** | ‘이 작업을 다른 기기로 가져가기’ 버튼으로 파일을 직접 옮김 | 기본 오프라인, 서버에 원문을 보관하지 않음, 교사가 범위·암호를 선택 | 낮음~중간 | **1단계 권장** |
| **B. 계정 기반 선택 백업함** | 웹에 ‘내 작업 보관함’을 만들고 필요한 세트만 올린 뒤 다른 기기에서 받음 | 서버 저장이 생기므로 명시 동의·암호화 키·보존·삭제 정책 필요 | 중간 | 2단계 후보 |
| **C. 선택형 암호화 자동 동기화** | 동기화를 켠 특정 작업공간만 여러 기기에 자동 반영 | 충돌·원격 삭제·새 기기 승인·키 복구·오프라인 큐까지 필요 | 높음 | 3단계, 충분한 파일럿 뒤 |

### A안: 암호화 작업 꾸러미

교사는 웹, Windows, Android 어디에서든 **‘다른 기기에서 이어서 작업’**을 선택합니다. 그 뒤 이동할 항목을 직접 고르고, 내보내기 암호를 설정해 하나의 `.eunma-work` 파일을 받습니다. 대상 기기에서는 같은 암호로 파일을 가져옵니다.

이 방식은 USB, 학교 보안 저장소, 교사가 관리하는 승인된 전송 수단을 사용할 수 있습니다. 파일을 어떤 클라우드에 올릴지는 교사의 선택이므로, EunmaStudio가 원문을 자동 보관하거나 전송하지 않습니다.

### B안: 계정 기반 선택 백업함

교사가 웹 계정에 로그인한 상태에서, 특정 작업 세트만 ‘암호화 보관함’에 올립니다. Windows와 Android는 교사가 명시적으로 연결한 기기에서만 이를 내려받습니다. 이 방식은 파일 이동을 줄이지만, 서버 보관과 계정 복구가 들어오므로 다음 단계의 법적·운영 준비가 필요합니다.

### C안: 선택형 암호화 자동 동기화

교사가 ‘이 작업공간만 동기화’를 켠 경우에만 변경 사항을 여러 기기로 전달합니다. 가장 편하지만, 같은 문항을 두 기기에서 수정했을 때의 충돌, 기기 분실, 원격 삭제, 키를 잊은 경우, 네트워크가 없는 학교 환경을 모두 해결해야 합니다. 따라서 초기 출시 기능으로는 권장하지 않습니다.

## 3. 권장 단계: A → B → C

### 1단계: 세 플랫폼 공통 암호화 이관

첫 번째 구현은 **웹·Windows·Android 모두에서 같은 형식의 암호화 작업 꾸러미를 내보내고 가져오는 기능**입니다. 자동 동기화는 하지 않으며, 교사가 눌러야만 파일이 생성·복원됩니다.

| 이관 범위 | 기본값 | 이유 |
|---|---|---|
| 메모·쪽지시험·검수 상태·출제 조건 | 포함 가능 | 작고 구조가 단순하며 교사 작업 연속성에 직접 도움 |
| 승인 문항·정답·해설·근거 요약 | 포함 가능 | 웹·PC·모바일 후속 검수에 필요 |
| 자료의 제목·출처·페이지·추출 발췌 | 포함 가능 | 근거 추적을 유지하되 파일 크기와 권리 위험을 낮춤 |
| 원본 PDF·이미지·첨부 파일 | 기본 제외, 교사 명시 선택 시만 | 대용량·저작권·민감 자료 위험이 가장 큼 |
| 대화 원문 | 기본 제외, 별도 선택 | 수업 메모·개인 정보가 섞일 수 있어 가장 보수적으로 취급 |
| API 키·세션·앱 잠금 정보·모델 파일 | 항상 제외 | 이동하거나 복원하면 안 되는 비밀·환경 정보 |

**충돌 처리**는 첫 단계에서 병합하지 않습니다. 이미 같은 식별자의 항목이 있으면 대상 기기에 ‘가져온 사본’으로 보관하고, 교사가 유지할 항목을 비교·선택합니다. 이를 통해 자동 병합으로 문항·정답·근거가 조용히 덮어써지는 위험을 피합니다.

### 2단계: 선택 백업함

1단계가 사용성과 파일 형식 안정성을 검증한 뒤, 웹 계정 안에 **기본 비활성 암호화 보관함**을 추가합니다. 교사가 보관함을 처음 켤 때 전송 대상, 보존 기간, 삭제 방식, 복구 불가 위험을 확인하고 동의합니다. 대상 기기 추가는 QR 또는 일회용 승인 코드로 수행합니다.

### 3단계: 작업공간별 암호화 동기화

2단계에서 교사들이 실제로 반복 이동하는 세트, 충돌 빈도, 복구 요청을 확인한 뒤에만 도입합니다. 동기화는 계정 전체가 아니라 **교사가 이름 붙인 작업공간별**로 켜며, 출시 예정 문항 세트는 기본적으로 비동기화 상태를 유지합니다.

## 4. 보안 통제 설계

| 통제 항목 | 1단계 작업 꾸러미 | 2~3단계 보관함·동기화 |
|---|---|---|
| 암호화 | 교사 암호에서 파생한 키로 파일 전체를 AES-256-GCM 암호화 | 서버에는 암호문만 저장, 기기별 키 관리 필요 |
| 키 소유 | 교사가 내보내기 암호를 보유 | 기본은 교사 키 소유, 복구 방식은 별도 선택·고지 |
| 전송 동의 | 내보내기·가져오기 화면마다 범위 요약 확인 | 처음 켤 때 범위·보존·삭제·새 기기 승인 동의 |
| 새 기기 승인 | 파일과 암호를 가진 교사가 직접 가져오기 | 기존 승인 기기 또는 QR/일회용 코드로 승인 |
| 삭제 | 원본을 자동 삭제하지 않음 | 로컬·서버·다른 기기 각각의 삭제 상태를 명시 |
| 충돌 | 사본으로 보관, 교사 선택 | 개정 번호·충돌 화면·원본 유지·해결 기록 필요 |
| 감사 흔적 | 내보내기/가져오기 시각·항목 수·성공/실패만 기기에 기록 | 동의·기기 승인·동기화·삭제 이벤트의 최소 메타데이터 기록 |

> **중요:** ‘암호화되어 있다’는 말만으로 충분하지 않습니다. 비밀 키를 누가 보유하는지, 암호를 잊으면 어떻게 되는지, 새 기기를 어떻게 승인하는지, 삭제가 어느 기기까지 적용되는지를 교사가 이해할 수 있는 문장으로 먼저 정해야 합니다.

## 5. 공통 데이터 계약 초안

세 플랫폼은 저장 엔진이 달라도 다음 공통 식별·개정 필드를 가져야 합니다.

| 필드 | 목적 |
|---|---|
| `objectId` | 플랫폼과 무관한 UUID. 가져오기·중복·충돌 판단의 기준 |
| `objectType` | 메모, 자료 메타데이터, 문항, 검수, 쪽지시험, 대화 등 구분 |
| `originPlatform` / `originDeviceId` | 어디서 최초 생성했는지 표시 |
| `revision` / `updatedAt` | 변경 순서와 비교 기준 |
| `deletedAt` | 즉시 영구 삭제가 아닌 삭제 의도 기록 |
| `sensitivity` | 일반 작업/수업 자료/출시 예정 문항 등 경고 수준 |
| `payloadVersion` | 앱 버전이 달라도 안전하게 해석하기 위한 형식 버전 |

파일 형식은 평문 JSON을 바로 옮기지 않고, **암호화 전 서명 가능한 표준 데이터 묶음**으로 만들고, 암호화 후에는 플랫폼이 공통으로 열 수 있는 단일 파일로 저장합니다. 원본 파일 자체는 포함 여부·용량·파일별 암호화가 추가로 필요하므로 1단계에서는 선택 항목으로 분리합니다.

## 6. 교사 화면 제안

각 플랫폼에 같은 이름의 **‘기기 간 작업 이어쓰기’** 메뉴를 둡니다.

| 화면 단계 | 교사에게 보여 줄 내용 |
|---|---|
| 1. 작업 선택 | 메모, 승인 문항, 쪽지시험, 자료 요약, 대화 중 무엇을 옮길지 체크 |
| 2. 보안 확인 | ‘원본 파일 포함 여부’, ‘대화 원문 포함 여부’, ‘원본은 삭제되지 않음’을 명확히 고지 |
| 3. 암호 설정/기기 승인 | 1단계는 내보내기 암호, 이후 단계는 새 기기 승인 |
| 4. 결과 확인 | 항목 수, 제외 항목, 충돌 사본 수, 복원 위치를 표시 |
| 5. 가져온 항목 검수 | 새로 가져온 문항은 자동 승인하지 않고 ‘가져온 항목’으로 분리 |

## 7. 지금 필요한 제품 결정

아래 세 가지는 구현 전에 결정해야 합니다.

| 결정 | 권장안 | 이유 |
|---|---|---|
| 첫 이동 대상 | 메모·쪽지시험·승인 문항·근거 요약 | 사용성은 높고 원본 파일보다 위험·용량이 낮음 |
| 원본 파일 이동 | 기본 제외, 명시 선택 | PDF·이미지는 권리·용량·민감도 위험이 큼 |
| 대화 원문 이동 | 기본 제외 | 개인적 대화·수업 맥락이 섞일 수 있으므로 별도 동의가 적절 |

## 8. 권고 결론

교사가 웹에서 준비하고 로컬에서 생성하는 흐름은 제품의 핵심 사용 시나리오이므로, 독립 저장소를 그대로 두되 **암호화 작업 꾸러미 이관을 다음 공통 기능 묶음으로 구현하는 것**을 권고합니다. 이는 당장의 불편을 줄이면서, 자동 동기화가 요구하는 복잡한 보안·법적·운영 책임을 성급히 떠안지 않는 균형안입니다.

자동 동기화는 편리하지만 출시 예정 문항·자료의 보안과 충돌 처리까지 제품 책임으로 가져옵니다. 따라서 1단계 이관 기능의 사용 기록과 교사 피드백을 본 뒤, 선택 백업함과 작업공간별 암호화 동기화로 확장하는 순서가 적절합니다.
