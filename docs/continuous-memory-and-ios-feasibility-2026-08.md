# 사용자 질문 요약 기억 및 iOS 병행 타당성 검토

## 결론

**사용자 질문 원문을 장기간 그대로 유지하기보다, 질문의 의도·핵심 변수·모델이 확정한 결론·남은 확인 과제를 짧게 기억하는 방식은 적절합니다.** 다만 “모델이 답했다”라는 사실만 남기면 `그 설명을 더 짧게`, `방금 정답 기준을 적용해 줘` 같은 지시가 무엇을 가리키는지 알 수 없습니다. 따라서 모델 답변의 원문은 버리되, 답변의 **결론과 작업 상태**만 구조화해 남기는 방식이 더 안전합니다.

| 기억 층 | 제안 보존 내용 | 목표 예산 | 용도 |
|---|---|---:|---|
| 현재 문맥 | 최근 사용자 질문 1~2개, 현재 질문 | 250자 내외 | 지시어·표현을 자연스럽게 연결 |
| 요약 기억 | 질문 의도, 핵심 대상·수치, 모델 결론, 미확정 항목 | 회차당 40~70자 | 이전 주제·결론을 장기 보존 |
| 자료 기억 | 자료명·쪽수·교사 확인 필요 여부 | 회차당 20~40자 | 출처와 검수 경계를 유지 |
| 원본 기록 | 기기 내 대화 목록 | 별도 저장 | 교사가 직접 확인·삭제 |

권장 요약 형태는 다음과 같습니다.

> `의도: 애국가 1~4절 요청 / 핵심: 가사 범위 / 처리: 요청 범위를 확인함 / 다음: 원하는 제공 방식 확인 필요`

이 방식은 원문 모델 답변을 프롬프트에 반복하지 않아 입력 토큰을 줄이지만, 모델이 이미 어떤 결론을 내렸는지는 잃지 않습니다. 최근 질문만 저장하는 방식보다 후속 질문의 정확도가 높고, 긴 답변 원문을 계속 주입하는 방식보다 컨텍스트·KV 캐시 부담이 작습니다. 요약은 별도 짧은 모델 호출로 생성하면 정확도가 높지만 한 번의 추가 추론이 필요합니다. 파일럿에서는 우선 규칙 기반 요약(제목·질문·핵심 명사·답변 상태)을 사용하고, 긴 대화에서만 짧은 모델 요약을 호출하는 혼합형이 합리적입니다.

## iOS 앱 병행 판단

**기술적으로는 가능하지만 Android 앱의 단순 포팅은 아닙니다.** LiteRT-LM은 iOS용 Swift API와 Metal 가속을 제공하며 `.litertlm` 모델을 네이티브 iOS 앱에서 실행할 수 있습니다.[1] 그러나 현재 Kotlin/Android UI, 다운로드 포그라운드 서비스, SharedPreferences, Android 공유 시트, 생체 인증, PDF·DOCX 출력은 SwiftUI·iOS 저장소·Files 공유·Face ID/Touch ID·Apple 문서 처리 체계로 각각 다시 구현해야 합니다. 공통으로 재사용 가능한 것은 프롬프트 계약, 모델 정책, 자료·문항·대화 데이터 계약, 보안 정책, 테스트 시나리오입니다.

| 범위 | 1인 기준 공수 | 포함 범위 | 판단 |
|---|---:|---|---|
| 기술 파일럿 | 약 14 인력주 | SwiftUI 홈·채팅, E2B 다운로드·해시·온디바이스 추론, 로컬 대화·기본 공유, 실기기 QA | Android 안정화 후 적합성 확인용 |
| Android 핵심 동등성 | 약 22 인력주 | 자료 처리, 문항 생성·검수, 잠금, 문서 공유, TestFlight, iPhone 기기 호환 | 실제 파일럿 전 최소 권장 범위 |
| 출시 준비 | 약 32 인력주 | 동등성 범위 + 접근성, 성능·발열 시험, 심사 자료, 개인정보·지원·회귀 시험 | 공개 배포 판단 범위 |

이는 **인력주(person-week)** 추정이다. 한 명이 전담하면 각각 약 3.5개월, 5.5개월, 8개월의 순차 작업에 해당한다. Android와 iOS 담당자가 둘이고 공통 계약·정책을 공유하면 표준 동등성은 약 14~16주, 출시 준비는 약 22~24주의 달력 기간으로 줄일 수 있으나, 모델 성능 시험과 App Review 대응은 완전히 병렬화되지 않는다.

Apple Developer Program은 App Store 배포와 TestFlight 사용을 위해 연 **99달러** 멤버십을 요구한다.[2] TestFlight는 최대 10,000명의 외부 테스터를 지원하지만, 외부 테스터 첫 빌드는 베타 심사를 거친다.[3] 또한 새 앱·업데이트에는 App Privacy 정보가 필요하며, 기기 밖으로 전송하지 않는 처리 자체는 Apple의 ‘수집’ 정의에 포함되지 않지만, 분석 SDK·오류 보고·원격 모델 다운로드 로그 등 실제 도입하는 모든 외부 전송은 정확히 고지해야 한다.[4] App Review는 충돌 없는 실기기 검증, 완성된 메타데이터·지원/개인정보 링크, 비자명 기능의 설명을 요구한다.[5]

## 권장 순서 — 현재는 구현 보류

현재 Android의 E2B 연속 대화 안정성, 발열·배터리 기준, 자료 처리·문서 공유, Play 내부 테스트가 끝나기 전에는 iOS 본개발을 시작하지 않는 것이 좋습니다. 그 뒤 iPhone 실기기 한 대에서 **2주 기술 스파이크**로 LiteRT-LM Swift 모델 초기화·Metal/CPU fallback·2,048토큰 안정성·E2B 발열을 확인하고, 통과 시에만 위 14 인력주 파일럿 범위를 승인하는 순서가 비용 위험을 가장 낮춥니다. 이 문서는 판단용이며 iOS 코드·계정·배포 작업은 수행하지 않았습니다.
